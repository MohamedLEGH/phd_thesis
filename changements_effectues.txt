COMMENT 1
--------------------------------------------------------------------------------
Affected section : Chapter 2 ("Model"), Section 2.3.1 "Synchronization"
                   file : template/chapter/model.typ

Reviewer comment (verbatim) :
  "In Section 2.3.1, \"Synchronization,\" the description of synchronization in
  overlay networks is somewhat confusing. At the beginning, the text says that
  the systems are fully asynchronous, but the thesis then introduces an abstract
  notion of time, which actually makes them synchronous. It would be useful to
  state this more clearly: that the model is synchronous, but that the protocols
  may be applicable in an asynchronous setting."

Change made :
  1. The opening paragraphs of the section (which discussed the time
     abstraction) were rewritten to state explicitly, from the outset, that the
     model adopted in this thesis is a SYNCHRONOUS, round-based model (time is
     partitioned into logical protocol cycles, and every node executes exactly
     one protocol step per cycle), and that this is a deliberate modeling choice
     made to keep the mathematical analysis and the simulation tractable.
     -> The word "synchronous" is now explicit in the presentation of the model
        (it was previously absent).

  2. A note was added at the end of the section (after the presentation of the
     two execution models, i.e. the synchronous cycle model and the sequential
     cycle model) clarifying that this synchronous, round-based model is a
     modeling abstraction, NOT an assumption about the physical execution of
     the protocols: in practice, the protocols can execute asynchronously,
     exactly as real-world peer-to-peer systems do (no global clock required,
     each node progresses at its own pace, cycles remain purely logical units).
     This claim is supported by the experimental validation reported in the
     Elevator chapter (reference @chap:elevator), where an asynchronous
     execution mode (nodes wait a random duration between cycles) yields the
     same qualitative behavior as the synchronous one.

  Note : the previous passage describing the asynchrony of real systems at the
         beginning of the section was removed to avoid redundancy with the
         end-of-section note (which now addresses the asynchronous setting).

Old text (section introduction, before modification) :
  "At the overlay level, however, synchronization still plays a conceptual role.
  In real-world peer-to-peer systems, nodes operate fully asynchronously: there
  is no global clock, and each node evolves at its own pace based on local events
  and message arrivals. While this behavior accurately reflects practical
  systems, it makes mathematical analysis and simulation significantly more
  complex. To enable a tractable and precise formalization, we introduce an
  abstract notion of time based on protocol steps and protocol cycles. These
  notions do not represent real time, but rather logical execution units that
  allow us to reason about the global evolution of the system in a structured
  manner."

New text (section introduction) :
  "At the overlay level, however, synchronization still plays a conceptual role.
  The model adopted in this thesis is a synchronous, round-based model: time is
  partitioned into logical protocol cycles, and we assume that every node
  executes exactly one protocol step per cycle. This is a deliberate modeling
  choice, made to keep the mathematical analysis and the simulation of the
  protocols tractable."

Text added at the end of the section (after the "sequential cycle model") :
  "The synchronous, round-based model described above is a modeling abstraction,
  not an assumption about the physical execution of the protocols. In practice,
  the protocols presented in this thesis can execute asynchronously, exactly as
  real-world peer-to-peer systems do: no global clock is required, each node
  progresses at its own pace, and cycles remain purely logical units. This is
  confirmed by the experimental validation reported in @chap:elevator, where an
  asynchronous execution mode — in which nodes wait a random duration between
  cycles — yields the same qualitative behavior as the synchronous one."

--------------------------------------------------------------------------------
Affected section : Chapter 3 ("Overlay Management in Peer to Peer Systems"),
                   Section 3.1 "Metrics", sub-section "Degree Distribution"
                   file : template/chapter/overlay.typ

Reviewer comment (verbatim) :
  "At the beginning of Chapter 3, when talking about degree distribution, the text
  mentions unstructured peer-to-peer overlays, but the term \"unstructured\" has not yet
  been defined. It is only defined later in the document."

Change made :
  The opening sentence of the Degree Distribution paragraph, which used the term
  "unstructured peer-to-peer overlays" before that term had been introduced (the
  structured/unstructured classification is only defined later in the chapter, in
  the "Structured Networks" section), was reformulated so that it no longer relies
  on the as-yet-undefined term. Since the statement (the outdegree is constrained by
  design and remains approximately constant, equal to the fixed size of the partial
  view) holds for all overlays under the model adopted in the thesis, not only for
  unstructured ones, it is now anchored in the system model instead of a network
  class.

Old text :
  "In most unstructured peer-to-peer overlays, the outdegree is constrained by design
  and remains approximately constant, as it corresponds to the fixed size of the
  partial view maintained by each node."

New text :
  "In the overlay model adopted in this thesis, the outdegree is constrained by design
  and remains approximately constant, as it corresponds to the fixed size of the
  partial view maintained by each node."

Affected section : Chapter 3 ("Overlay Management in Peer to Peer Systems"),
                   Section 3.2 "Structured Networks"
                   file : template/chapter/overlay.typ

Reviewer comment (verbatim) :
  "I found the formulation that says "structured peer-to-peer overlay networks are mostly
  implemented through distributed hash tables" somewhat confusing. It is actually the
  other way around: distributed hash tables are built by defining a structured peer-to-peer
  overlay."

Change made :
  The opening sentence of the paragraph that described structured networks in terms of
  Distributed Hash Tables was reformulated so that the DHT/structured-overlay relationship
  is now stated correctly: a DHT is presented as an application built on top of a
  structured peer-to-peer overlay (rather than structured networks being "implemented
  through" DHTs). The rest of the paragraph (how nodes and data are mapped, consistent
  hashing, etc.) is unchanged.

  Other occurrences of a similar relation were checked elsewhere in the manuscript:
  they either state the relationship correctly (e.g. "Structured overlays are typically
  co-designed with a specific application, such as distributed hash tables or key-value
  stores") or refer to "DHT-based systems" without replicating the problematic
  "implemented through" formulation, so no other change was needed.

Old text :
  "Structured peer-to-peer networks are most commonly implemented through
  Distributed Hash Tables (DHTs), which provide a scalable and fully decentralized
  mechanism for data storage and retrieval."

New text :
  "Distributed Hash Tables (DHTs), which provide a scalable and fully decentralized
  mechanism for data storage and retrieval, are among the most widely deployed
  applications built on top of structured peer-to-peer networks."

COMMENT 4
--------------------------------------------------------------------------------
Affected section : Chapter 3 ("Overlay Management in Peer to Peer Systems"),
                   Section 2.3 "Peer Sampling Service" (introduction of the service)
                   file : template/chapter/overlay.typ

Reviewer comment (verbatim) :
  " It is not strictly true that a peer-sampling service returns an overlay graph that
  converges toward a random graph, because a random graph does not have a fixed
  out-degree, whereas the graph resulting from a peer-sampling service has a constant
  out-degree. So, the graph resembles a random graph, but it is not strictly a random
  graph in the Erdos-Renyi sense"

Change made :
  The sentence claiming that the overlay graph induced by a peer sampling service
  "converges toward a random graph" was reformulated. It now states that this graph
  resembles a random graph in which each node has a fixed number of outgoing neighbors
  (i.e. a random k-out graph, more formally a directed random graph with fixed
  outdegree, defined in the Appendix), rather than implying a convergence to a strict
  Erdős-Rényi random graph. This correction also anchors the wording to the formal
  definition already present in the Appendix (@def:Directed-Random-Graph), which was
  previously never referenced from the body of the manuscript.

  Other occurrences of a "random graph" relation were reviewed: the remaining mentions
  either use hedged wording ("approximate", "approach", "closest approximation",
  "converges to the properties of a random graph") or are descriptions of results
  reported from the literature, so they were left unchanged.

Old text :
  "Since the goal of a peer sampling service is to return a uniformly random node, the
  overlay graph induced by such a service naturally converges toward a random graph
  (see @sec:random-graph)."

New text :
  "Since the goal of a peer sampling service is to return a uniformly random node, the
  overlay graph induced by such a service resembles a random graph in which each node
  has a fixed number of outgoing neighbors — a random k-out graph, more formally a
  directed random graph with fixed outdegree (see @def:Directed-Random-Graph)."

Affected section : Chapter 4 (Elevator), Section 4.2.6 "Lift protocol"
                   file : template/chapter/elevator.typ

Reviewer comment (verbatim) :
  "In Section 4.2.6, the formulation "we hope that our protocol will have no impact" or
  "we hope that our protocol will be more efficient" is somewhat unusual. It would be
  better to use a formulation such as "we designed our protocol to be more efficient,"
  and so on."

Change made :
  The formulation of intent expressed with "we hope that" in the presentation of the
  Lift protocol was replaced by an assertive statement of design intent: Lift is now
  described as being designed to be more efficient than Elevator in terms of resilience
  when Byzantine nodes are active, and to have no impact on protocol performance and
  convergence when Byzantine nodes are absent.

  Other occurrences of vague/hedged formulations similar to "we hope" were reviewed:
  the expression "is the author's hope" at the very end of the thesis (Conclusions) is
  kept, as it belongs to the concluding remarks on the expected impact of the work,
  where such a formulation is appropriate; the expression "is expected to serve as CHs"
  expresses a statistical expectation, not an unassertive wish, so it was left
  unchanged.

Old text (relevant sentence) :
  "If Byzantine nodes are active, we hope that our new protocol will be more efficient
  than Elevator in terms of resilience, and if Byzantine nodes are not active, we hope
  that the protocol will have no impact on protocol performance and convergence towards
  hubs."

New text (relevant sentence) :
  "Lift is designed to be more efficient than Elevator in terms of resilience when
  Byzantine nodes are active, while having no impact on protocol performance and
  convergence toward hubs when Byzantine nodes are absent."
