General Comment (1)

Reviewer comment (verbatim) :
  "First, I would like to point out that, since the thesis presents what is
  essentially an architecture for decentralized learning, the presentation would
  benefit from introducing this architecture (consisting of the four layers) at the
  very beginning. This could possibly be done in the introduction, in Chapter 3, or
  in an additional short chapter before describing the actual Elevator and Lift
  protocols. Because this architecture is then later reused across different
  machine-learning algorithms, it would be useful to have a sense from the beginning
  that the thesis has a unitary view."

Change made :
  The four-layer architecture (Network / Overlay / Aggregation / Application) that
  underpins the thesis is now introduced at the very beginning of the Introduction,
  at the head of the "Contributions" section. The new passage presents this
  architecture, embeds the layered-diagram figure (the same cetz schematic that is
  used in the HEAL chapter), explains the key design intuition (the overlay layer is
  engineered so as to make efficient global aggregation possible), and states, to the
  best of our knowledge, that such an architecture for decentralized machine learning
  — in which a structured overlay is explicitly the substrate for ML aggregation,
  with independently replaceable layers — has not been proposed before. It then
  announces that the four contributions (Elevator, Lift, HEAL, FLAIR) instantiate
  this architecture layer by layer, giving the reader the unitary view requested from
  the outset.

Affected section : Chapter 2 ("Model"), Section 2.3.1 "Synchronization"
                   file : template/chapter/model.typ

Reviewer comment (verbatim) :
  "In Section 2.3.1, \"Synchronization,\" the description of synchronization in
  overlay networks is somewhat confusing. At the beginning, the text says that
  the systems are fully asynchronous, but the thesis then introduces an abstract
  notion of time, which actually makes them synchronous. It would be useful to
  state this more clearly: that the model is synchronous, but that the protocols
  may be applicable in an asynchronous setting."

Change made :
  1. The opening paragraphs of the section (which discussed the time
     abstraction) were rewritten to state explicitly, from the outset, that the
     model adopted in this thesis is a SYNCHRONOUS, round-based model (time is
     partitioned into logical protocol cycles, and every node executes exactly
     one protocol step per cycle), and that this is a deliberate modeling choice
     made to keep the mathematical analysis and the simulation tractable.
     -> The word "synchronous" is now explicit in the presentation of the model
        (it was previously absent).

  2. A note was added at the end of the section (after the presentation of the
     two execution models, i.e. the synchronous cycle model and the sequential
     cycle model) clarifying that this synchronous, round-based model is a
     modeling abstraction, NOT an assumption about the physical execution of
     the protocols: in practice, the protocols can execute asynchronously,
     exactly as real-world peer-to-peer systems do (no global clock required,
     each node progresses at its own pace, cycles remain purely logical units).
     This claim is supported by the experimental validation reported in the
     Elevator chapter (reference @chap:elevator), where an asynchronous
     execution mode (nodes wait a random duration between cycles) yields the
     same qualitative behavior as the synchronous one.

  Note : the previous passage describing the asynchrony of real systems at the
         beginning of the section was removed to avoid redundancy with the
         end-of-section note (which now addresses the asynchronous setting).

Old text (section introduction, before modification) :
  "At the overlay level, however, synchronization still plays a conceptual role.
  In real-world peer-to-peer systems, nodes operate fully asynchronously: there
  is no global clock, and each node evolves at its own pace based on local events
  and message arrivals. While this behavior accurately reflects practical
  systems, it makes mathematical analysis and simulation significantly more
  complex. To enable a tractable and precise formalization, we introduce an
  abstract notion of time based on protocol steps and protocol cycles. These
  notions do not represent real time, but rather logical execution units that
  allow us to reason about the global evolution of the system in a structured
  manner."

New text (section introduction) :
  "At the overlay level, however, synchronization still plays a conceptual role.
  The model adopted in this thesis is a synchronous, round-based model: time is
  partitioned into logical protocol cycles, and we assume that every node
  executes exactly one protocol step per cycle. This is a deliberate modeling
  choice, made to keep the mathematical analysis and the simulation of the
  protocols tractable."

Text added at the end of the section (after the "sequential cycle model") :
  "The synchronous, round-based model described above is a modeling abstraction,
  not an assumption about the physical execution of the protocols. In practice,
  the protocols presented in this thesis can execute asynchronously, exactly as
  real-world peer-to-peer systems do: no global clock is required, each node
  progresses at its own pace, and cycles remain purely logical units. This is
  confirmed by the experimental validation reported in @chap:elevator, where an
  asynchronous execution mode — in which nodes wait a random duration between
  cycles — yields the same qualitative behavior as the synchronous one."

                   file : template/chapter/overlay.typ

Reviewer comment (verbatim) :
  " It is not strictly true that a peer-sampling service returns an overlay graph that
  converges toward a random graph, because a random graph does not have a fixed
  out-degree, whereas the graph resulting from a peer-sampling service has a constant

  definition already present in the Appendix (@def:Directed-Random-Graph), which was
  previously never referenced from the body of the manuscript.

  Other occurrences of a "random graph" relation were reviewed: the remaining mentions
  either use hedged wording ("approximate", "approach", "closest approximation",
  "converges to the properties of a random graph") or are descriptions of results
  reported from the literature, so they were left unchanged.

Old text :
  "Since the goal of a peer sampling service is to return a uniformly random node, the
  overlay graph induced by such a service naturally converges toward a random graph
  (see @sec:random-graph)."

New text :
  "Since the goal of a peer sampling service is to return a uniformly random node, the
  overlay graph induced by such a service resembles a random graph in which each node
  has a fixed number of outgoing neighbors — a random k-out graph, more formally a
  directed random graph with fixed outdegree (see @def:Directed-Random-Graph)."

Affected section : Chapter 6 (HEAL/FLAIR), FLAIR protocol, Overlay Layer
                   (resource-aware cluster-head selection and the use of VRF)
                   file : template/chapter/heal.typ

Reviewer comment (verbatim) :
  "The description of the FLAIR protocol states that the protocol uses verifiable random
  functions to guarantee that the election of cluster heads remains tamper-resistant and
  verifiable. However, there is nothing that prevents a cluster head from cheating about
  its available CPU, RAM, GPU, or bandwidth. Given this, do verifiable random functions
  really provide anything useful?"

Change made :
  Two passages that over-claimed the guarantee provided by verifiable random functions
  (VRF) were reformulated so that the text now states precisely what a VRF guarantees
  and what it does not, and explicitly situates the discussion in a fault-free setting.

  - In the general description of the protocol, the claim that the VRF "prevents
    manipulation of elections and guarantees fairness" was replaced by a more precise
    statement: the VRF produces a random value that cannot be biased by the node and is
    publicly verifiable, but actually verifying such a value requires an external
    mechanism exposing the node's VRF output (e.g. a public register), which falls
    outside the scope of the thesis. In the fault-free setting considered, the VRF
    primarily ensures fairness by making the election draw unpredictable.

  - In the resource-aware CH election paragraph, the claim that the VRF "guarantees
    that elections remain tamper-resistant" was replaced by a statement that the VRF
    makes the election draw unpredictable and publicly verifiable, preventing a node
    from biasing its own draw. It is now made explicit that this is addressed in a
    non-adversarial setting in which nodes are assumed to report their resources
    honestly, so that the resource score R_n remains self-reported, and that detecting
    nodes misreporting their capabilities (CPU, RAM, GPU, bandwidth) to inflate their
    election probability is an open and non-trivial direction.

Affected section : Chapter 6, FLAIR protocol, Aggregation Layer
                   file : template/chapter/heal.typ

Reviewer comment (verbatim) :
  "In the description of the aggregation layer, it is initially unclear why each cluster
  runs a fully contained learning process, and it becomes clear only later that the
  actual cluster heads change at each iteration. This should be made clear from the

Change made :
  A short paragraph was added right after the statement that each cluster runs a fully
  self-contained learning process. It now explains, from the outset, that this design is

  also indicates that this point is developed in detail in the architectural properties
  below, so that the reader is no longer left puzzled at the Aggregation Layer stage.

  "This design is made possible by the fact that cluster-heads are re-elected at each
  round: although each cluster learns in isolation during a given round, the rotation
  of cluster-heads causes the aggregated models to be progressively redistributed
  across clusters over successive rounds, ensuring global mixing without any
  inter-cluster communication. This point is developed in detail in the architectural

                   file : template/chapter/heal.typ

Reviewer comment (verbatim) :
  "The simulation compares FLAIR with HEAL, Gaia, and gossip learning. However, it is

Change made :
  The description of Experiment 1 was clarified. It is now stated explicitly that (i)
  this experiment is the ONLY one that compares FLAIR with the baselines (C-FL, Gaia,

  FLAIR on its own and therefore do not involve any of the other baselines.
